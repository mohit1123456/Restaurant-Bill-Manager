RESTAURANT BILL MANAGER — PROJECT PLANNING

==================================================
PROBLEM STATEMENT
==================================================

It’s Diwali and the restaurant is slammed. The kitchen has a long menu, and by evening some favourites — the paneer, the special thali — run out and shouldn’t be orderable any more.

On top of that, marketing has four offers running at once:

- Flat ₹50 off
- 10% off on orders above ₹500, capped at ₹100
- And other offers

Every bill also needs:

- Packing charge
- Delivery fee unless it’s a large order
- GST on top

Everything must add up to the exact paisa.

Right now the cashier is doing this by hand and getting it wrong, customers are arguing at the counter, and everyone wants to see a clear break-up of how the total was reached.

BUILD A PRICING ENGINE THE BILLING SCREEN CAN TRUST.

The messy real-world details are the whole point. The solution must handle each rule correctly.

The intended calculation flow is:

Plain order total
        ↓
Offers / discounts
        ↓
Fees
        ↓
Tax
        ↓
Final total


==================================================
PROJECT INFORMATION
==================================================

Project Name:

Restaurant Bill Manager

Project Description:

This project helps restaurants handle their bills with the latest offers and discounts without any hassle.

Recommended improved description:

Restaurant Bill Manager is a restaurant billing and pricing application that automatically calculates order totals, applies eligible offers, adds applicable fees and GST, and provides a transparent bill breakdown — ensuring accurate billing down to the exact paisa.

==================================================
MODULE 4 — OFFERS & DISCOUNT ENGINE
==================================================

Offers should be represented as reusable rules rather than hardcoded into UI components.

Example discount rule:

DiscountRule

- type
- eligibility condition
- percentage or fixed amount
- maximum discount
- priority
- stacking behavior


Example:

Offer:
10% off on orders above ₹500
Maximum discount: ₹100

For an order of:

₹1,500

10% = ₹150

But maximum discount = ₹100

Therefore:

Actual discount = ₹100


==================================================
DISCOUNT STACKING
==================================================

This is an important business-rule decision.

Suppose:

Subtotal = ₹1,000

Offer 1 = ₹50 flat discount
Offer 2 = 10% discount

Possible interpretations:

Option A — Sequential stacking:

₹1,000
- ₹50
= ₹950

10% of ₹950
= ₹95

Final:
₹855


Option B — Independent calculation:

₹50 + ₹100
= ₹150 discount

Final:
₹850


Option C — Only one offer:

Best discount = ₹100

Final:
₹900


The actual behavior must be determined from the assessment requirements.

If the requirements are ambiguous, choose an explicit policy and document the assumption in REASONING.md.

Do NOT leave this behavior hidden in code.


==================================================
MODULE 5 — PACKING CHARGE
==================================================

Every bill requires a packing charge.

The charge should be configurable.

Do not scatter hardcoded values across React components or Django views.

For example:

PACKING_CHARGE = ₹20

The exact rule should be confirmed from the assessment requirements.


==================================================
MODULE 6 — DELIVERY FEE
==================================================

The problem states:

There is a delivery fee unless the order is a large order.

The implementation should represent this as an explicit rule.

Example:

DELIVERY_FEE = ₹50
FREE_DELIVERY_THRESHOLD = ₹1000

Therefore:

Order < ₹1000
    → Delivery fee applies

Order >= ₹1000
    → Free delivery


If the actual assessment specifies different values, use those values.

If not specified, choose reasonable assumptions and document them in REASONING.md.


==================================================
MODULE 7 — GST / TAX
==================================================

GST must be calculated accurately.

The project specifically requires exact paisa-level calculation.

Recommended approach:

Represent money internally as INTEGER PAISE.

Example:

₹125.50
=
12550 paise


₹10.00
=
1000 paise


Avoid using floating point for monetary calculations.

For example, do not rely on:

0.1 + 0.2

for billing calculations.


Recommended internal representation:

₹125.50 → 12550


Then calculations can use integer arithmetic wherever possible.
